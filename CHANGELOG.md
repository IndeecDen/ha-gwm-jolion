# Changelog

## 0.1.0-alpha.19.3

Полевой и frontend-релиз: исправлена трактовка живых состояний сидений/окон и полностью переработана карточка `custom:gwm-jolion-remote-card`.

### Remote card: вид сверху

- SVG автомобиля переведён на вид сверху: капот слева, багажник справа;
- кузов подсвечивается по состоянию замка: locked / unlocked / unknown;
- в правом верхнем углу отображаются T-Box Online/Offline и 4-сегментный GSM-индикатор;
- под автомобилем добавлена компактная строка статусов: двигатель, климат, топливо, пробег, двери, окна, багажник;
- отдельные двери анимируются по существующим door binary sensors;
- открытый багажник визуально отводится от кузова;
- работающий двигатель подсвечивает моторный отсек пульсацией;
- включённый климат показывает анимированные потоки воздуха в салоне;
- водительское окно `2210001` визуально использует подтверждённую шкалу `1=закрыто`, `3=частично открыто`, `2=полностью открыто`;
- остальные окна пока не получают выдуманную физическую позицию: при общем `windows_open` показывается общий визуальный alert;
- фары вынесены в отдельный SVG/CSS-слой и больше не зависят от состояния двигателя; слой останется выключенным до подтверждения telemetry-кода света;
- капот остаётся статическим до появления подтверждённого hood status.

### Окна

- старый decoder `raw == 0 -> open` удалён;
- `raw=1` теперь трактуется как закрыто;
- `raw=2` и `raw=3` трактуются как незакрытое окно;
- неизвестные значения, включая `0`, не угадываются и возвращают unknown;
- aggregate `windows_open` учитывает multistate-значения;
- индивидуальные window binary sensors временно имеют нейтральные названия по коду, пока marker-тест не подтвердит физическую позицию `2210002..2210004`.

### Подогрев передних сидений

- `vehicleBasicsInfo.leftFrontSeat/rightFrontSeat` больше не используются как fallback живого состояния;
- живое состояние берётся только из `2220001` / `2220002`;
- принята шкала для обоих передних сидений: `0=off`, `1=low`, `2=medium`, `3=high`;
- если live-сигнал отсутствует, сущность остаётся unavailable вместо ложного уровня из сохранённого preset.

### Tests / docs / version

- добавлены тесты multistate-window decoder;
- добавлен тест, что `vehicleBasicsInfo` не подменяет live seat state;
- добавлен тест приоритета `2220001/2220002`;
- обновлены `README.md`, `ROADMAP.md`, `PROTOCOL.md`, `manifest.json`, internal `VERSION` и frontend cache version;
- версия интеграции — `0.1.0-alpha.19.3`.

## 0.1.0-alpha.19.2

Расширенный диагностический релиз перед физическими тестами автомобиля. Цель — не потерять потенциально полезные поля GWM, которые раньше не попадали в Protocol Capture.

### Protocol Capture schema 2

- schema JSONL повышена до `2`;
- для каждого `items[].code` сохраняется `signal_units`, если GWM прислал единицу измерения;
- сохраняется `signal_item_seen_keys` — набор имён полей, реально встреченных внутри элементов `items[]`;
- добавлен `status_meta` с безопасными верхнеуровневыми полями `getLastStatus`: `acquisitionTime`, `uploadTime`, `updateTime`, `oilQty`, `percentageOfOil`, `charge`, `serviceStatus`, `deviceType`, `command`;
- для `status_meta` сохраняется diff `previous → value` в `status_meta_changes`;
- добавлен `status_structure` — структура всего `getLastStatus` только с именами ключей и типами, без значений; благодаря этому неизвестные верхнеуровневые и вложенные поля можно заметить без риска утечки VIN/координат;
- добавлены `vehicle_basics_seen_keys` и `vehicle_basics_structure`, чтобы видеть неизвестные поля `vehicleBasicsInfo`, даже если их значения не входят в безопасный whitelist;
- добавлены `tbox_meta`, `tbox_meta_changes` и `tbox_structure` для безопасного анализа `findStatus` / T-Box;
- потенциально чувствительные неизвестные значения автоматически не сохраняются: для них остаётся только структура ключей/типов;
- VIN, точные координаты, телефон/аккаунт, credentials, IMSI/ICCID, vehicle/device ID по-прежнему не записываются в Protocol Capture.

### GPS / карта Home Assistant

- существующая сущность `device_tracker` **Местоположение** остаётся источником GPS для стандартной карты Home Assistant;
- latitude/longitude теперь безопасно приводятся к `float`, чтобы строковые координаты GWM корректно отображались на карте;
- для GPS-трекера добавлена иконка `mdi:car`;
- координаты используются только самой GPS-сущностью и не добавляются в Protocol Capture/диагностический экспорт.

### Тесты / документация

- добавлены unit-тесты расширенного capture record: units, `percentageOfOil`, safe metadata, structures и изменения meta-полей;
- обновлены `README.md`, `ROADMAP.md`, `CHANGELOG.md`, `manifest.json` и внутренний `VERSION`;
- новых GWM remote-команд, command payload и предположений о назначении неизвестных кодов нет;
- версия интеграции — `0.1.0-alpha.19.2`.

## 0.1.0-alpha.19.1

Диагностический hotfix Protocol Capture: длинная тестовая сессия больше не может вытеснить исходный telemetry baseline из стандартного экспорта Home Assistant.

### Экспорт Protocol Capture

- лимит свежих записей в `protocol_capture → session_export` увеличен с 2000 до **5000**;
- первый корректный `type=refresh` с `baseline=true` сохраняется отдельно и **не входит** в лимит 5000;
- при длинной сессии экспорт содержит **первый baseline + 5000 самых свежих корректных записей**, максимум 5001 запись;
- короткая сессия экспортируется целиком;
- полный JSONL-журнал на диске не обрезается и продолжает хранить всю сессию в `/config/gwm_jolion_protocol_capture/`;
- если baseline отсутствует в повреждённом/старом журнале, экспорт сохраняет до 5000 последних корректных записей и выставляет `baseline_preserved=false`;
- добавлены поля `valid_records_in_file`, `baseline_preserved`, `recent_records_limit` и `selection=first_baseline_plus_latest`;
- `truncated` теперь показывает, что часть корректных записей не вошла именно в ограниченную копию диагностики;
- добавлены unit-тесты сохранения baseline, выбора последних записей, полного экспорта короткой сессии и значения лимита 5000.

### Документация / версия

- обновлены `README.md`, `ROADMAP.md`, `CHANGELOG.md`, `manifest.json` и внутренний `VERSION`;
- новых GWM remote-команд, payload или telemetry mappings нет;
- версия интеграции — `0.1.0-alpha.19.1`.

## 0.1.0-alpha.19

Подготовка Protocol Capture к полевой диагностической сессии без добавления новых GWM remote-команд.

### Диагностика Protocol Capture

- стандартная команда Home Assistant `Скачать диагностику` теперь включает текущую JSONL capture-сессию прямо в диагностический JSON;
- экспорт ограничен 2000 корректными записями, чтобы очень длинная сессия не раздувала diagnostics без ограничений;
- экспорт сообщает `records_in_file`, `records_exported`, `truncated`, `invalid_lines` и `read_error`;
- в diagnostics дополнительно сохраняются время последней capture-записи, источник последнего обновления, число последних изменений и последняя пользовательская метка;
- автоматические capture-записи по-прежнему не содержат VIN, точные координаты, телефон/аккаунт, credentials и device identifiers;
- пользовательские метки явно помечены как user-supplied и не должны использоваться для персональных или секретных данных.

### Сенсор и метки тестов

- добавлен диагностический сенсор `Запись протокола GWM` со состояниями `disabled`, `recording`, `error`;
- атрибуты сенсора показывают имя файла, число записанных строк, время и источник последней записи, `last_changes_count`, последнюю метку и ошибку записи;
- добавлен сервис `gwm_jolion.add_capture_marker` с полем `label`;
- метка записывается отдельной JSONL-строкой `type=marker` и не изменяет telemetry baseline / предыдущие raw-значения;
- метки нормализуются в одну строку и ограничены 80 символами;
- baseline теперь определяется наличием предыдущего telemetry snapshot, поэтому даже метка до первого refresh не может сломать первый baseline.

### Тесты / протокол

- добавлены unit-тесты marker records, проверки пустых/слишком длинных меток и bounded diagnostics export;
- `ROADMAP.md` обновлён для `alpha.18` и `alpha.19`;
- новых GWM command payload, remote-команд и предположений о неизвестных кодах в этой версии нет;
- версия интеграции обновлена до `0.1.0-alpha.19`.

## 0.1.0-alpha.18

Добавлен отдельный режим записи протокола для физических тестов автомобиля и поиска неизвестных GWM-кодов.

### Режим поиска GWM-кодов

- в настройках интеграции добавлен переключатель `Режим поиска GWM-кодов (JSONL-журнал)`, по умолчанию выключенный;
- при включении создаётся отдельная сессия в `/config/gwm_jolion_protocol_capture/gwm_code_search_*.jsonl`;
- каждый успешный опрос GWM дописывается в тот же файл одной независимой JSONL-строкой;
- первый успешный опрос записывается как baseline с полным снимком всех увиденных raw-сигналов и безопасного `vehicleBasicsInfo`;
- последующие опросы содержат полный снимок и вычисленный diff `previous -> value` для GWM-сигналов и `vehicleBasicsInfo`;
- неизвестные telemetry-коды сохраняются вместе с текущими значениями, чтобы можно было сопоставлять их с физическими действиями в автомобиле;
- для известных кодов в diff добавляются имя сигнала, описание и текущий статус проверки протокола;
- ручная кнопка `Обновить данные` помечает запись как `source=manual_button`;
- обычный coordinator polling помечается как `source=poll`;
- опрос после успешной удалённой команды помечается как `source=remote_command`;
- проверочный опрос перед удалённым запуском двигателя помечается как `source=remote_start_guard`;
- запись JSONL выполняется вне event loop, а ошибка записи журнала не прерывает штатный polling автомобиля.

### Диагностика и приватность

- capture-журнал не включает VIN, точные координаты, телефон/аккаунт, пароли, PIN, access token, IMSI/ICCID, vehicle ID и device identifiers;
- в Home Assistant diagnostics добавлены состояние Protocol Capture, имя активного файла, число успешно записанных строк и последняя ошибка записи;
- добавлены unit-тесты baseline, diff известных/неизвестных сигналов и последовательного JSONL append;
- Python checks, Hassfest и HACS validation проходят для нового режима.

### Протокол / remote-команды

- новых remote-команд или новых GWM command payload в этой версии не добавлялось;
- существующие remote-команды продолжают работать без изменения их payload;
- версия интеграции обновлена до `0.1.0-alpha.18`.

## 0.1.0-alpha.14

Исправление зависания очереди удалённых команд и отображения неизвестных состояний в карточках.

### Удалённые команды

- конечные ошибки T5 теперь завершают polling сразу вместо ожидания полного 300-секундного timeout;
- коды `1000`, `2000` и подтверждённый промежуточный код `11` продолжают считаться незавершёнными;
- после выхода из command lock публикуется отдельное обновление `in_progress=false`, поэтому карточки больше не остаются заблокированными после завершённой/ошибочной команды;
- карточки ориентируются на фактический `in_progress`, а не на потенциально устаревшее состояние `pending`;
- новых remote payload автомобиля нет.

### Карточки / статусы

- основная карточка не предлагает действие по замку, двигателю, климату, окнам или багажнику, если соответствующая телеметрия недоступна;
- карточка-пульт показывает `нет данных` вместо ложных `закрыто`, `выключено`, `offline` для неизвестных основных состояний;
- информационные плитки GSM/T-Box, GPS и климата также различают реальное отрицательное состояние и отсутствие данных;
- добавлены unit-тесты классификации T5 result codes.

## 0.1.0-alpha.9

Исправление трактовки поля `oilQty` российского GWM API.

### Исправлено

- `oilQty` больше не трактуется как уровень топлива;
- диагностическая сущность переименована в `Уровень масла GWM (0–8)`;
- в карточке блок `Топливо GWM` заменён на `Масло`;
- уровень масла отображается как 8-сегментная шкала без вычисления процентов;
- обычный уровень топлива по-прежнему берётся из фактических литров и объёма бака;
- cache-busting встроенной карточки обновлён до `0.1.0-alpha.9`.

### Обоснование

В реальных ответах GWM `oilQty` не коррелирует с количеством топлива: при баке около 82–84% поле может иметь значение `4`. Российские реализации GWM также используют `oilQty` как уровень масла. Поэтому в этой версии поле отделено от топливной телеметрии.
